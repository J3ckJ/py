# Пайплайн браузера: почему `top` дёргается, а `transform` нет

Монитор ~60 Гц → бюджет кадра ~16.6 мс, из них вам ~10 мс. Не уложились — кадр выпал, анимация «мылит». Это не «компьютер слабый». Это вы заставили браузер делать Layout на каждом wheel.

Источник модели: [web.dev — Rendering performance](https://web.dev/articles/rendering-performance), [RenderingNG](https://developer.chrome.com/docs/chromium/renderingng-architecture).

## Пять ступеней

```
JavaScript → Style → Layout → Paint → Composite
```

1. **JS** — поменяли DOM или стили (или CSS animation тикнула без JS).
2. **Style** — какие правила применимы, computed style.
3. **Layout (reflow)** — геометрия. Ширина одного блока может сдвинуть всю страницу.
4. **Paint** — залить пиксели слоя: текст, тени, картинки, `background`, `box-shadow`.
5. **Composite** — сложить GPU-текстуры слоёв: сдвинуть, повернуть, сменить opacity, проскроллить.

Три типичных пути кадра:

| Что меняете | Путь | Цена |
| --- | --- | --- |
| `width`, `height`, `top`, `left`, `font-size` | Style → **Layout** → Paint → Composite | дорого |
| `color`, `background`, `box-shadow`, `filter`* | Style → **Paint** → Composite | средне |
| `transform`, `opacity` (свой слой) | Style → **Composite** | дёшево |

\* `filter` и `backdrop-filter` коварны: часто создают слои, но paint/blend дорогой. Не анимируйте blur на всём герое.

## Слои (compositor layers)

Браузер может вынести элемент в отдельную GPU-текстуру. Тогда `transform: translate3d(...)` двигает текстуру, не перерисовывая буквы.

Как элемент попадает на слой (эвристики Chromium, упрощённо):

- анимация `transform`/`opacity`;
- `will-change: transform`;
- `transform: translateZ(0)` (старый хак);
- видео, canvas, iframe;
- иногда `position: fixed` + opacity/filter.

`will-change` на `body` или `*` — **layer explosion**: VRAM, лишний blend, иногда размытый текст. Ставьте на конкретный движущийся узел и снимайте после анимации.

Демо: [`../sites/01-composite.html`](../sites/01-composite.html) — слева анимация `top` (layout), справа `transform` (composite).

## Скролл на compositor

Chromium умеет скроллить страницу **на compositor thread**, даже если главный поток занят JS — *если* нет scroll-handler'а, который читает layout и пишет стили каждый кадр.

Именно поэтому:

```js
window.addEventListener('scroll', () => {
  el.style.top = window.scrollY * 0.3 + 'px'; // убивает дешёвый скролл
});
```

хуже, чем CSS `animation-timeline: scroll()` на `transform`.

Если всё же нужен JS (canvas, WebGL, video.currentTime):

- один rAF-цикл, не работа в `scroll`;
- в `scroll` только ставить флаг `dirty = true`;
- читать `scrollY` / `getBoundingClientRect` пачкой, не смешивать read/write (layout thrash).

## Главный поток vs compositor vs GPU

- **Main**: DOM, JS, layout, часть paint.
- **Compositor**: слои, скролл, compositor-only анимации.
- **GPU**: растеризация тайлов, blend.

Canvas 2D и WebGL рисуют из main (или worker + OffscreenCanvas). Тяжёлый `drawImage` 4K каждый кадр съест main, даже если CSS идеален. Apple выносил сборку Flow-кадров в worker.

## Практическое правило

Анимируйте **положение, масштаб, поворот, прозрачность**. Всё остальное — смена состояния (hover цвет кнопки — ок), не 60 fps скролл-скраб.

`prefers-reduced-motion: reduce` — отключайте scrub и оставляйте статичный кадр. Это не «урезанная версия для слабых», это контракт с вестибулярной системой.
