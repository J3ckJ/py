# Дескрипторы: механизм, на котором стоит «обычный» Python

Если понять одну внутреннюю вещь языка — пусть это будут дескрипторы. Методы, `@property`, `classmethod`, `staticmethod`, слоты, FastAPI-не-дескрипторы vs Flask-прокси — всё это ветки одного дерева.

## Определение

Дескриптор — объект, у которого есть `__get__`, `__set__` или `__delete__`. Он живёт **на классе**. Когда вы пишете `obj.x`, а `x` найден в типе `obj`, Python может вызвать `x.__get__(obj, type(obj))` вместо того чтобы вернуть сам `x`.

- **Data descriptor**: есть `__set__` или `__delete__`. Побеждает `__dict__` экземпляра.
- **Non-data descriptor**: только `__get__`. Экземплярный атрибут побеждает.

Функции — non-data descriptors. Поэтому `obj.method` становится bound method, но вы можете записать `obj.method = 1` и затенить его.

## Как из функции получается метод

У объекта-функции есть `__get__`. При доступе через экземпляр он возвращает `types.MethodType(fn, obj)`: тонкую обёртку, которая подставляет `self`. При доступе через класс возвращается сама функция (в 3.x unbound methods больше нет).

```python
class C:
    def f(self):
        return self

c = C()
assert c.f.__func__ is C.f
assert c.f() is c
```

Это не синтаксис `def` внутри класса. Это дескриптор, который сработал при атрибутном доступе. Можно сделать то же руками: положить функцию в класс после `class` — методы заработают.

## `@property`

`property` — data descriptor. Хранит `fget`/`fset`/`fdel`. Используется и для вычисляемых полей, и для *ленивой* инициализации, и чтобы запретить запись (`@property` без setter).

В Django `cached_property` (и Werkzeug) — дескриптор, который после первого `__get__` **записывает результат в `__dict__` экземпляра**. Следующий доступ идёт уже не через дескриптор (если это non-data… внимание: обычный `cached_property` аккуратно сделан так, чтобы после записи победил `__dict__`). Это паттерн: «один раз посчитать, дальше — обычный атрибут».

## `classmethod` / `staticmethod`

- `classmethod.__get__` биндит **класс**, не экземпляр. Нужен как альтернативный конструктор (`from_json`, `model_validate` — последнее у Pydantic на самом деле `classmethod` поверх Rust).
- `staticmethod.__get__` возвращает сырую функцию. Это способ сказать «лежит на классе для пространства имён, `self` не нужен». Часто лучше обычная функция модуля; staticmethod оправдан, когда важна принадлежность к API класса.

## `__set_name__`

С 3.6 дескриптор может узнать, в какой класс и под каким именем его положили:

```python
class Field:
    def __set_name__(self, owner, name):
        self.name = name
    def __get__(self, obj, owner):
        if obj is None:
            return self
        return obj.__dict__[self.name]
```

ORM-колонки, Pydantic `computed_field`, валидаторы — все нуждаются в имени поля. Раньше это делали метаклассами; `__set_name__` снял часть этой нужды. Метаклассы остались для *компиляции всей схемы сразу*.

## Слоты

`__slots__ = ("x", "y")` создаёт дескрипторы-слоты на классе и **убирает** `__dict__` (если не добавить `"__dict__"` в слоты). Экономия памяти, запрет случайных атрибутов, чуть быстрее доступ. В C-расширениях аналог — фиксированный layout `PyObject`. В чистом Python слоты — редкость в прикладном коде и норма в объектах, которых миллионы (графы, AST, ORM instance state).

SQLAlchemy `InstanceState` — отдельный объект состояния рядом с вашим mapped instance; это не слоты вашего класса, но та же идея: *служебные данные не смешивать с пользовательскими атрибутами как попало*.

## `__getattribute__` vs дескриптор

`LocalProxy` в Werkzeug не является «просто дескриптором на модуле». Он — объект, который при **любом** доступе (`request.args`, `request.method`, `request['foo']`) идёт в `ContextVar`. Реализация: куча dunder, проксированных через `_ProxyLookup`, и `_get_current_object()`.

Это тяжелее дескриптора, потому что прокси должен притворяться *уже существующим* объектом, а не атрибутом класса. Дескриптор решает «как читать `C.x`». Прокси решает «как сделать так, чтобы имя в модуле всегда указывало на чужой объект».

## Маркеры, которые только притворяются дескрипторами

`Depends()` в FastAPI — не дескриптор. Это значение по умолчанию параметра, которое `inspect.signature` потом находит. Разница критична:

- Дескриптор срабатывает при **атрибутном доступе**.
- Маркер срабатывает, когда **фреймворк смотрит сигнатуру**.

Если вы напишете свой DI «как property» — получите другой жизненный цикл. FastAPI сознательно выбрал inspect + defaults, потому что хочет аннотации *и* значения по умолчанию как данные для OpenAPI.

## Минимальный дескриптор, который стоит написать самому

См. `examples/02_descriptors.py`. Идея: лог доступа, валидация при записи, хранение значения в `obj.__dict__[self.private_name]`, чтобы сам дескриптор не держал per-instance состояние (иначе дескриптор, висящий на классе, делит значение между всеми экземплярами — классический баг).

## Где это в живом коде

- Каждый метод любого класса.
- Flask 3.2 `LocalProxy(_cv_app, "request")`.
- Pydantic field collection + `__pydantic_validator__` на классе (не дескриптор, но сосед: данные живут на классе после метакласса).
- Django `cached_property` для `WSGIRequest.GET`.
