# Исключения, контексты, управление ресурсами

Исключения в Python — и ошибки, и управление потоком (`StopIteration`, `GeneratorExit`). Зрелый код отличает одно от другого.

## Объект исключения

`raise ValueError("x")` создаёт экземпляр. `except ValueError as e` привязывает имя. Цепочка: `raise New from orig` ставит `__cause__`; неявный `from` при `raise` внутри `except` ставит `__context__`. `from None` глушит контекст — используйте, только когда старый traceback вреден пользователю.

`except*` (3.11, ExceptionGroup) распаковывает группы. Нужен, когда параллельный код (task groups, asyncio.TaskGroup) собирает несколько ошибок.

С 3.14 скобки в `except A, B` больше не обязательны в новой форме `except A, B` без скобок (PEP 758) — читайте changelog, линтеры ещё спорят о стиле. Смысл тот же: кортеж типов.

## Что ловить

Ловите **конкретное**. `except Exception` — на границе системы (view, CLI, worker job), где вы логируете и отвечаете 500. В библиотечном коде — узкий тип.

Не ловите `KeyboardInterrupt` и `SystemExit` через `except Exception` — они наследуют `BaseException`. `finally` и контекстные менеджеры всё равно отработают.

`StopIteration` в генераторе — протокол. Не поднимайте его вручную из обычных функций «чтобы выйти из for» — это сломает вызывающего. С 3.7 RuntimeError, если StopIteration утекает из корутины.

## `with` как единственный честный способ держать ресурс

Файл, сокет, транзакция, lock, Session, HTTP-ответ со стримом — всё, у чего есть «открыл/закрыл». Идиома:

```python
with open(path) as f:
    data = f.read()
```

Эквивалент try/finally, но нельзя забыть `close`. Для нескольких ресурсов — вложенные `with` или скобки:

```python
with (
    get_conn() as conn,
    conn.cursor() as cur,
):
    ...
```

`contextlib.ExitStack` / `AsyncExitStack` — когда набор ресурсов динамический. FastAPI буквально кладёт три `AsyncExitStack` в ASGI scope: файлы формы, request-scoped yield, function-scoped yield. Это промышленное использование того же протокола, что и `open()`.

## Генераторный `contextmanager`

```python
@contextmanager
def session():
    s = Session()
    try:
        yield s
        s.commit()
    except:
        s.rollback()
        raise
    finally:
        s.close()
```

Код после `yield` — teardown. Если генератор не дошёл до `yield` — enter упал, exit не должен путаться. `contextlib` это обрабатывает.

pytest yield-фикстуры — тот же паттерн: `next(gen)` в setup, второй `next` в teardown, ждут `StopIteration`.

## Контекстные переменные (PEP 567)

`contextvars.ContextVar` — состояние, привязанное к задаче/контексту, не к потоку как `threading.local` (хотя копируется в потоки по правилам). Flask 3.2 хранит `AppContext` в `ContextVar`. ASGI-middleware, порождающие task groups, должны понимать: копирование контекста — часть контракта.

Free-threaded build по умолчанию копирует context в новые `threading.Thread` (`thread_inherit_context=True`). GIL-сборка — нет. Код, который полагался на «в новом потоке пустой context», на 3.14t ведёт себя иначе.

## Логирование ошибок

Стандарт: `logger.exception(...)` внутри `except`, не `print(traceback)`. В веб-стеке исключение часто превращают в Response на границе (`ExceptionMiddleware`, Django `convert_exception_to_response`). Не глотайте исключение в глубине ORM «на всякий случай».

## `try/finally` и `return` в `finally`

PEP 765 (3.14) ужесточил контроль потока в `finally`: `return`/`break`/`continue` там маскировали исключения. Линтер и новые версии языка против этого. Ресурс закрывайте, значение возвращайте снаружи.

## Где это в живом коде

- Flask `wsgi_app`: `try/except/finally` вокруг `ctx.push()` / `ctx.pop(error)` — контекст обязан сняться даже при падении view.
- requests `Session.send` + `resp.close()` на редиректах.
- SQLAlchemy `Session.flush`: при ошибке транзакция сессии откатывается.
- pytest `call_and_report`: setup/call/teardown как три фазы, ошибка setup пропускает call.
