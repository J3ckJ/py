# CPython: что исполняет ваш `.py`

Язык Python не предписывает байткод. CPython предписывает себе. Если вы профилируете, пишете C-extension или спорите про GIL — вы уже в реализации.

## Конвейер

```
source → tokenize → PEG parse (AST) → compiler (symtable, CFG) → code object → eval loop
```

`compile()` / `dis.dis()` показывают code object: `co_code` (байты), `co_consts`, `co_varnames`, `co_names`. С 3.11 байткод specialized и «adaptive»: адаптивные инструкции могут специализироваться под наблюдаемые типы (`LOAD_ATTR` → per-type cache). Это причина, почему «прогретый» цикл быстрее первого круга.

Посмотреть: `examples/04_bytecode.py`.

## Кадр, стек, eval loop

Вызов функции создаёт frame (`PyFrameObject` / с 3.11 более компактные frames). У кадра есть указатель на instruction, локалы, стек значений. Eval loop в `Python/ceval.c` (и generated `generated_cases.c.h` из `Python/bytecodes.c`) — `switch` по опкодам.

С 3.14 есть **новый тип интерпретатора** (tail-calling / computed goto варианты в зависимости от платформы и сборки): те же опкоды, другая диспетчеризация, меньше overhead на каждый instruction. 3.15: официальные Windows x64 бинарники используют tail-calling interpreter; JIT заметно усилен.

Это важно практически так: микрооптимизации вида «заменить `x += 1` на `x = x + 1`» почти никогда не стоят вашего времени. Стоят: меньше вызовов Python из горячего цикла, больше работы в C/Rust (numpy, pydantic-core, regex), алгоритмы, I/O.

## Трёхуровневое исполнение (3.13–3.15)

Упрощённо, как описывает CPython internals:

1. **Tier 1** — байткод + адаптивная специализация.
2. **Tier 2** — трассы микро-опов (uops), оптимизатор трасс.
3. **JIT** (экспериментальный, в официальных macOS/Windows 3.14 бинарниках уже есть) — uops в машинный код через stencils (`Python/jit.c`, `Tools/jit`).

Не пишите код «под JIT». Пишите предсказуемые типы в горячих циклах: специализация и JIT любят стабильные shapes. Гетерогенные списки и megamorphic `obj.attr` остаются медленными.

## Объект в C

Каждый объект начинается с заголовка `PyObject`: refcnt (в GIL-сборке) + указатель на `PyTypeObject`. Тип содержит слоты: `tp_hash`, `tp_iter`, `tp_as_number`, … Вызов `len(x)` в горячем пути — это `PyObject_Size` → слот типа, не поиск `__len__` в dict, если слот заполнен.

Пользовательские классы — heap types. Их экземпляры обычно имеют `__dict__` и опционально `__weakref__`. Отсюда цена «чистого Python объекта» vs `int`/`list`, написанных на C.

## Модули расширения

`.so`/`.pyd` экспортируют `PyInit_name`. Limited API / Stable ABI (PEP 384 и дальше) позволяет собирать колёса, пережившие версию Python. Free-threaded build — **другой ABI** (`t` в теге, например `cp314t`). Расширение, не объявившее поддержку, при импорте **включает GIL обратно** для процесса.

Поэтому «поставили 3.14t и numpy не готов» выглядит как «потоки снова не параллелятся», а не как импорт-ошибка. Смотрите `sys._is_gil_enabled()` и https://py-free-threading.github.io/.

## Несколько интерпретаторов

С 3.14 `concurrent.interpreters` — отдельные изолированные рантаймы в одном процессе (PEP 734). Это не потоки и не multiprocessing: своя GIL (в классической сборке) / своё состояние, обмен — через очереди, не через общие Python-объекты как попало.

Имеет смысл как модель акторов без pickle-цены multiprocessing, когда расширение и память процесса общие. Экосистема ещё молодая; для большинства приложений 2026 года — `asyncio` + процессы + опционально 3.14t.

## Что смотреть в исходниках CPython, если решитесь

Не начинайте с `ceval.c`. Начните:

1. `Include/object.h` / `Include/object.h` layout.
2. `Objects/typeobject.c` — как устроен тип.
3. `Lib/` — stdlib на Python (часто понятнее, чем C).
4. `InternalDocs/` — jit, qsbr, gc.

Разбор всего CPython — отдельный репозиторий. Здесь достаточно модели, чтобы читать профилировщик и чужие C-extensions.
