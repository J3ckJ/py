# Как читать чужой Python-репозиторий за час

Чеклист, которым я пользовался, разбирая requests/Flask/FastAPI/pytest/Django.

## 15 минут: контур

1. README — какой контракт (CLI, library, framework).
2. `pyproject.toml` / `setup.cfg` — зависимости. Они выдают стек: есть `starlette` → ASGI; есть `urllib3` → sync HTTP; есть `pluggy` → хуки.
3. Каталоги: `src/pkg/` vs `pkg/` на корне. Тесты где.
4. Точка входа: `__main__.py`, `[project.scripts]`, `app = Flask(__name__)`.

## 20 минут: горячий путь

Выберите *один* пользовательский вызов. Для HTTP-клиента — `get()`. Для фреймворка — один view. Для pytest — один `test_`.

Grep не по слову «core», а по имени публичной функции. Читайте вниз по вызовам, игнорируя утилиты нормализации URL, пока не упрётесь в I/O.

Рисуйте список из 10–15 функций. Если список разросся до 50 — вы свернули не туда.

## 15 минут: состояние и граница I/O

Найдите класс, который живёт дольше одного вызова (`Session`, `Client`, `Flask`, `SchemaValidator` на классе). Найдите место, где байты покидают Python (urlopen, send, cursor.execute, file.write). Архитектура = всё между ними.

## 10 минут: тесты как документация

Откройте тесты на этот горячий путь. Они покажут инварианты, которые авторы считают священными (редиректы, timeout default, order middleware).

## Чего не делать

- Не читать `utils.py` первым. Там болото.
- Не начинать с `contrib/`.
- Не «изучать паттерны» вместо пути запроса.
- Не копировать архитектуру Pydantic в свой CRUD: у вас нет Rust-ядра и миллиона пользователей.

## После часа

У вас должно быть: диаграмма из блоков, место состояния, место I/O, один паттерн расширения (adapter, hook, middleware, metaclass). Этого достаточно, чтобы чинить баг. Остальное добирается по мере нужды.
