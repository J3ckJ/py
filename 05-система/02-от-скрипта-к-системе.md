# От скрипта к системе

Минимальная лестница. Не прыгайте через ступени.

## Скрипт

Один файл, `if __name__ == "__main__"`, pathlib, `subprocess`, никаких глобальных Session. Логирование `basicConfig`. Это честно для утилит.

## Пакет

`src/mypkg/`, `pyproject.toml`, тесты рядом, публичные функции с аннотациями. Конфиг — dataclass или pydantic на входе CLI, не `os.environ` в глубине случайных модулей (читать env можно в одном `settings.py`).

## Сервис

Граница HTTP: FastAPI (API) или Django (админка, формы, монолит). Один request — один ORM Session / один unit of work. Timeout на исходящем HTTP. Структурные логи (request-id из ContextVar).

Healthcheck, graceful shutdown, не `while True: pass`.

## Система

Несколько процессов: web, worker (очередь), scheduler. Общая БД — источник правды, не память воркера. Идемпотентность jobs. Миграции как код. Наблюдаемость: метрики, traces; в 3.15 frame pointers по умолчанию помогают системным профайлерам.

Free-threaded Python — опция после профилировки, не фундамент.

## Чего не делать «потому что так в FAANG»

- Микросервис на каждый CRUD.
- Kubernetes для одного процесса.
- Pydantic на каждый внутренний DTO.
- Async ORM, если у вас sync-команда и 50 RPS.
- Копировать архитектуру CPython JIT.

## Связь с этим репозиторием

Если пишете HTTP API — прочитайте FastAPI + httpx + один из ORM. Если CLI — pytest + pathlib, без фреймворка. Если библиотека — как requests: тонкий фасад, Session, адаптер, тесты на mock transport.

Карта языка (01–02) нужна всегда: без имён/объектов вы не поймёте ни один из этих этажей.
